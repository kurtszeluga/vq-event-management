## Phase 1 - Registration Security

| Item | Status | Notes |
| --- | --- | --- |
| Stop returning member phone and billing address before identity verification | Completed | Public lookup returns only profile existence and the required verification step. Contact, membership, and billing details are returned only after verification. |
| Require Firebase authentication for signed-in/password users | Completed | The server verifies the Firebase ID token, registration email, and linked profile UID. |
| Replace phone-number fallback with a Resend one-time email code | Completed | Six-digit codes expire after 10 minutes, allow five attempts, limit sends, and are stored only as hashes. |

| 2026-07-25 | Found and fixed the real cause of profile saves failing: the `users` update rule could not be evaluated. Firestore charges every expression a rule evaluates against a hard ceiling of 1000 per request, and a write that will be refused has to evaluate all three branches before it can answer "no" - so a refusal costs the sum of them. The rule called `validUser()`, a thirty-field sweep, inside each branch; rules do not memoise, so one update evaluated it up to three times and blew the ceiling. Firestore reports that as a plain `permission-denied`, which is why it looked like an ordinary rules refusal, why deploying changed nothing, why every clause passed when checked by hand against the live document, and why it failed identically for a General User and an Admin. The emulator surfaced it in one run: "Unable to evaluate the expression as the maximum of 1000 expressions to evaluate has been reached." Three changes: owner self-edits now use `validSelfProfileEdit()`, a small `diff().affectedKeys()` validator that also pins the change to seven fields, making role, status, permissions and every membership field immutable on that path by construction rather than by twelve separate comparisons; `membershipFieldsUnchanged()` is rewritten from twelve three-clause comparisons to one `affectedKeys().hasAny()`; and the admin branches share a single `validUserAdminUpdate()` that keeps the key whitelist and the role/status/permissions integrity but no longer re-type-checks fields the write is not touching (`validUser()` still guards `create`). The deliberate trade is that an admin could store a badly typed non-privilege field such as a numeric phone. `profileTagsUnchanged()` became unused and was removed. Added `tests/rules/users-self-update.test.js` (9 tests, `npm run test:rules`, wired into CI with a JDK step) - the project's first Firestore rules tests, covering owner save, refusal of role/permission/membership escalation, cross-user writes, and both admin paths.
